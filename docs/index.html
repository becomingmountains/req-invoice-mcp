How it works

MCP (Model Context Protocol) is a standard way to give AI assistants tools. This server gives yours six tools that talk to the Request Network API, a payment protocol that has settled on-chain invoices since 2017.

  1. You ask your assistant to bill someone.

  2. The server creates the invoice on Request Network and returns a payment link. The invoice gets a unique payment reference on-chain.

  3. The payer opens the link and pays from their own wallet. The reference ties the payment to your invoice automatically, so there's no matching by hand.

  4. You ask "did they pay?" and the assistant checks the invoice and shows the transaction.

No wallet, no spending. The server never holds a private key and never signs a transaction. You give it the address that receives money. A receive-only address can't be drained.

Quick start

1. Get your free credentials

  1. Open dashboard.request.network and sign in with your wallet.
  2. Set up a receiving route: the network, wallet and token you want to be paid in.
  3. On the route, click Manage → Client IDs → Generate and copy the Client ID.
  4. Copy the route's Route ID too. It looks like 0xWallet@eip155:1#ABCD1234:0xToken.

2. Add the server to your assistant

Needs Node.js 20 or newer. Add this to your MCP client's config (Cursor: .cursor/mcp.json, VS Code: .vscode/mcp.json, desktop apps: their MCP settings file):

{
  "mcpServers": {
    "req-invoice": {
      "command": "npx",
      "args": ["-y", "github:becomingmountains/req-invoice-mcp"],
      "env": {
        "REQUEST_CLIENT_ID": "your-client-id",
        "REQUEST_ORIGIN": "https://your-allowed-domain.example",
        "REQUEST_DESTINATION_ID": "0xYourWallet@eip155:1#ABCD1234:0xTokenAddress",
        "REQUEST_PAYEE": "0xYourWallet"
      }
    }
  }
}

3. Try it

Restart your assistant and ask: "Create a payment link for 25 USDC."

Configuration

All settings are environment variables in your MCP client config. Nothing is stored by the server.

VariableRequiredWhat it's for
REQUEST_CLIENT_IDthis or API keyClient ID from the dashboard.
REQUEST_API_KEYthis or Client IDServer-side API key, if you have one. Takes priority over the Client ID.
REQUEST_ORIGINwith Client IDAn origin matching the Client ID's allowed domain. The API checks it.
REQUEST_DESTINATION_IDfor linksYour Route ID. Turns on create_payment_link.
REQUEST_PAYEEsometimesDefault wallet that gets paid by create_invoice. Needed with an API key; with a Client ID the route's wallet is used.
REQUEST_API_URLnoAPI base URL. Defaults to https://api.request.network. Must be https.

Tools

Your assistant picks the right tool from what you say. Here's what each one does.

create_payment_link creates

Bills someone and returns a hosted link where they can pay in their own wallet. Uses the network and token of your receiving route. The easiest way to get paid.

Input: amount, e.g. "250", in your route's token.

"Send me a payment link for 250 USDC."

create_invoice creates

Creates an invoice in any supported token and network, or bills a USD amount paid in crypto.

InputNotes
amountPlain decimal, e.g. "19.99".
paymentCurrencyToken and network to be paid in, e.g. USDC-base, USDC-mainnet, ETH-sepolia-sepolia.
invoiceCurrencyOptional. Defaults to paymentCurrency; use USD to bill dollars.
payeeOptional. Wallet that gets paid; defaults to REQUEST_PAYEE.
payerOptional. Wallet expected to pay.
referenceOptional. Your note or invoice number, up to 200 characters.

"Invoice 0xAb…12 $1,200 for March consulting, paid in USDC on Base, reference INV-042."

check_invoice read-only

Paid or not, with the amount, payer and transaction hash once paid.

Input: requestId.

"Has INV-042 been paid?"

list_invoices read-only

Everything created with your credentials, newest first, marked PAID or UNPAID.

Inputs: optional walletAddress, limit (1–100), offset.

"Who still owes me money?"

get_payment_transactions read-only

For the payer: the unsigned transactions needed to pay an invoice, a token approval if needed and then the payment. Flags low balance or gas. The payer signs them in their own wallet.

Inputs: requestId, optional payerWallet.

"What do I need to sign to pay this invoice from 0x9c…e1?"

find_currency read-only

Looks up currency IDs to use as paymentCurrency.

Inputs: symbol and/or network.

"What's the currency ID for USDC on Arbitrum?"

For payers

Paying never goes through this server. A payer has two options:

  • Open the payment link and pay with any browser wallet. Most people will do this.
  • Pay programmatically. An agent with its own wallet calls get_payment_transactions, reviews the result, then signs and sends with its own tooling.

Automating payments? Use a separate wallet holding only a small budget, never your main wallet, and set spending limits in whatever signs the transactions.

Testing on Sepolia

Try the whole flow with test money first.

  1. Create a fresh wallet just for testing. Whatever you use is public on-chain.
  2. In the dashboard, set up a receiving route on Sepolia and copy its Route ID and a Client ID.
  3. Get test ETH for gas from a Sepolia faucet, and test USDC from faucet.circle.com.
  4. Ask your assistant for a payment link, pay it from a second test wallet, then ask whether it's been paid.

Safety

  • Can't move funds. No private keys, no signing, no sending. Tools only create and read invoices.
  • Strict inputs. Addresses, amounts and IDs are validated before any network call, so a confused or manipulated model can't reach other API paths.
  • Credentials stay put. Keys live in your MCP client config and are never included in tool output or error messages.
  • Read-only tools are marked read-only, so clients can auto-approve them and ask before anything that creates an invoice.
  • Open source and tested. Every tool is covered by tests that run on each commit.

FAQ

Does it cost anything?

The server is free and MIT licensed. Request Network credentials are free. Payers pay normal network gas, and Request Network may apply its own protocol fees; check their docs.

Which networks and tokens?

Whatever Request Network supports, including Ethereum, Base, Arbitrum, Optimism, Polygon, BNB Chain, Sepolia and more, with USDC, USDT, DAI, ETH and others. Use find_currency to check.

Is this official?

No. It's an independent community project built on Request Network's public API.

How is this different from x402?

x402 handles instant pay-per-request payments. This covers invoices, where someone is billed now and pays later, with a record that ties the payment to the bill. They complement each other.

Something broke. Where do I report it?

Open an issue on GitHub.
